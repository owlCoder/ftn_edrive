PulseNet

Distribuirana platforma za community i društveno umrežavanje
Poglavlje I

Opis projekta

PulseNet je distribuirana fullstack web aplikacija za community i društveno umrežavanje. Aplikacija ima deo koji korisnik vidi i koristi u pretraživaču (frontend — React + TypeScript), i serverski deo koji radi kao REST API, prihvata zahteve i podatke čuva u MySQL bazi podataka sa replikacijom (backend — Node.js + Express + mysql2).

„PulseNet funkcioniše kao kombinacija Reddit-a i Discord-a — korisnik kreira nalog, pridružuje se ili kreira tematske zajednice (community-je), objavljuje postove, komentariše, lajkuje sadržaj i prati druge korisnike. Svaka zajednica ima moderatore i članove, a sadržaj je organizovan u kategorije putem tagova. Sistem je distribuiran — baza podataka radi u Master-Slave replikaciji sa automatskim failoverom i balansiranjem čitanja između replika."
I.1 — Tehničke karakteristike sistema

U tehničkom smislu, ovo je CRUD sistem sa autentifikacijom, hijerarhijom uloga i distribuiranom bazom podataka. Sistem obuhvata četiri M:N relacije između ključnih entiteta. Kritična komponenta je sloj za upravljanje konekcijama ka bazi koji podržava replikaciju, health check i failover. Ceo frontend je deployovan kao statički sajt, dok backend radi kao Node.js serverless ili klasični server.

Poglavlje II

Funkcionalni zahtevi

II.1 — Registracija i prijava (Autentifikacija)

Autentifikacija je proces kojim sistem proverava identitet korisnika. Korisnik se registruje, unosi lozinku koja se čuva heširana u bazi podataka korišćenjem bcrypt biblioteke (nikad u originalnom formatu). Prilikom uspešne prijave, server generiše i vraća JSON Web Token (JWT) koji klijent čuva u localStorage pretraživača putem useAuth hook-a unutar autentifikacionog kontekstualnog prostora.

  • Forma za registraciju sadrži: korisničko ime, ime i prezime, email, lozinku, kratku biografiju i profilnu sliku (base64 string ili binarna datoteka putem multer biblioteke)
  • Prijava proverava kredencijale na serveru i pri uspehu vraća JWT token koji se čuva u localStorage; pri svakom sledećem učitavanju aplikacije token se čita iz localStorage i korisnik ostaje prijavljen
  • Odjava briše token iz localStorage i šalje POST /api/auth/logout koji beleži odjavu u evidenciji događaja (audits)
  • Zaštićene rute nisu dostupne bez važećeg tokena — korisnik se automatski preusmerava na /login
  • Validacija svakog polja mora biti implementirana i na klijentskoj (React) i na serverskoj strani (validatori podataka)
JWT token sadrži enkodovane podatke o korisniku: user_id, username i role. Server verifikuje token pri svakom zahtevu putem authMiddleware funkcije. Nikad ne čuvati osetljive podatke (lozinku, lične podatke...) unutar JWT payload-a.
II.2 — Upravljanje zajednicama (Communities)

Korisnik može kreirati zajednicu i postati njen vlasnik i moderator (moderator), ili se pridružiti tuđoj zajednici kao član (member). Ovo je prva M:N relacija — jedan korisnik može biti član više zajednica, a jedna zajednica može imati više korisnika. Vezna tabela community_members sadrži atribut role koji definiše ulogu korisnika unutar zajednice (moderator / member), i joined_at timestamp.

  • Kreiranje zajednice sa nazivom, opisom, pravilima, avatarskom slikom i oznakom javnosti (javna / privatna)
  • Pregled svih zajednica čiji je korisnik član (dashboard i sidebar)
  • Moderator zajednice može prihvatati ili odbijati zahteve za prijem u privatnu zajednicu
  • Moderator može dodeliti ili oduzeti moderatorsku ulogu drugim članovima
  • Napuštanje zajednice uklanja korisnika — svi njegovi postovi ostaju u zajednici
  • Brisanje zajednice moguće samo od strane moderatora — kaskadno briše sve postove, komentare i lajkove zajednice
II.3 — Objave (Posts) i tagovanje

Objava (post) pripada jednoj zajednici (strani ključ community_id) i kreira je jedan korisnik (strani ključ author_id). Svaka objava može biti označena sa jednom ili više oznaka (tags) koje opisuju temu — ovo je druga M:N relacija između posts i tags tabela.

  • Kreiranje objave sa naslovom, sadržajem u Markdown formatu, opcionim medijskim prilogom (URL slike) i tagovima
  • Pregled objava zajednice sa sortiranjem po: najnovije, najpopularnije (po broju lajkova), najkomentarisanije
  • Filtriranje objava po tagovima — frontend logika bez poziva ka serveru
  • Korisnici mogu lajkovati ili ukloniti lajk sa objave — frontend prikazuje ukupan broj lajkova u realnom vremenu
  • Stranica detalja objave prikazuje pun sadržaj, sve komentare u hijerarhijskom prikazu (root komentari + odgovori)
  • Izmena i brisanje objave dostupni samo autoru ili moderatoru zajednice
II.4 — Komentari i odgovori

Komentar (comment) pripada jednoj objavi (strani ključ post_id) i može imati roditeljski komentar (strani ključ parent_id, nullable — za root komentare je NULL). Komentar mogu lajkovati korisnici — ovo nije zasebna M:N relacija već deo comment_likes koji se implementuje analogno post_likes.

  • Dodavanje komentara na objavu (root nivo) ili kao odgovor na postojeći komentar (ugneždeni nivo — maksimalno 2 nivoa dubine)
  • Lajkovanje komentara — korisnik može lajkovati/unlajkovati svaki komentar jednom
  • Sortiranje komentara unutar objave po: najnovije, najpopularnije
  • Brisanje sopstvenog komentara — soft delete (prikazuje se kao „[komentar obrisan]") kako bi se sačuvao kontekst odgovora
  • Moderator može označiti komentar kao narušavanje pravila i prijaviti ga — označeni komentar dobija vidljivi indikator
II.5 — Praćenje korisnika (Follow sistem)

Korisnici mogu pratiti jedni druge — ovo je četvrta M:N relacija (self-referencing) na tabeli users. Vezna tabela user_follows sadrži follower_id i following_id sa followed_at timestamp-om. Ovaj sistem napaja personalizovani feed korisnika.

  • Praćenje / prestanak praćenja drugog korisnika jednim klikom
  • Profil korisnika prikazuje broj pratilaca i broj korisnika koje prati
  • Feed stranica prikazuje najnovije objave iz zajednica kojima korisnik pripada I objave korisnika koje prati — kombinovani feed sortiran po vremenu
  • Pretraga korisnika po korisničkom imenu (za praćenje ili za tagovanje u komentarima sa @username sintaksom)
II.6 — Dashboard korisnika
  • Personalizovani feed: objave iz zajednica i od praćenih korisnika
  • Pregled svih zajednica kojima korisnik pripada (sidebar)
  • Pregled sopstvenih objava i komentara na profilnoj stranici
  • Vizuelni prikaz tagova kojima je korisnik najaktivniji (frontend logika — izračunava se iz sopstvenih objava)
  • Lista pratilaca i praćenih korisnika sa mogućnošću uklanjanja iz liste pratilaca
II.7 — Administrativni panel

Dostupan isključivo korisnicima sa ulogom admin. Pokušaj pristupa od strane korisnika mora biti blokiran i na klijentskoj i na serverskoj strani upotrebom mehanizma zaštićenih ruta / auth middleware.

  • Pregled svih registrovanih korisnika, zajednica i objava u sistemu
  • Promena uloge korisnika (promovisanje u admina ili vraćanje na standardnog korisnika)
  • Brisanje objava i zajednica koje krše uslove korišćenja
  • Pregled kompletnog audit loga aktivnosti — ko je, kada i šta uradio
  • Health Dashboard — pregled statusa i stanja svih čvorova baze podataka (master + slave replike); prikazuje koji čvorovi su aktivni, koji su u degradovanom stanju i koji su u ispadu
  • Ručno pokretanje failover procedure iz admin panela u slučaju da auto-failover nije aktivan
  • Upravljanje globalnim tagovima — kreiranje i brisanje tagova dostupnih za korišćenje pri kreiranju objava
II.8 — Pregled funkcionalnosti po ulogama
👁 Gost — može

Pregledati javne zajednice i objave, otvoriti stranicu za registraciju i prijavu.

👁 Gost — ne može

Kreirati sadržaj, lajkovati, komentarisati, pratiti korisnike ili pristupiti fedu i admin panelu.

👤 Korisnik — može

Kreirati i pridruživati se zajednicama, objavljivati postove, komentarisati, lajkovati sadržaj, pratiti korisnike, uređivati sopstveni profil.

👤 Korisnik — ne može

Pristupiti admin panelu, menjati tuđe objave i komentare, brisati zajednice čiji nije moderator.

⭐ Admin — može

Sve što korisnik može i dodatno: upravljati svim korisnicima, zajednicama i objavama, čitati audit log, videti health status čvorova baze, upravljati tagovima.

⭐ Admin — ne može

Direktno čitati ili menjati privatne poruke između korisnika — to ostaje zaštićeni prostor korisnika.

Poglavlje III

M:N relacije u bazi podataka

Sistem sadrži četiri M:N relacije. Svaka se realizuje posebnom veznom tabelom sa stranim ključevima prema obe strane relacije i opcionim dodatnim atributima koji opisuju tu vezu. Vezne tabele nisu puke spojnice — svaka nosi podatke koji imaju semantičko značenje.

M:N Relacija 1 — Korisnici ↔ Zajednice
users ⟷ communities
Vezna tabela: community_members
role ENUM('moderator','member') joined_at DATETIME status ENUM('active','pending','banned')

Jedan korisnik može biti član više zajednica, jedna zajednica može imati više korisnika. Atribut role definiše nivo pristupa unutar konkretne zajednice. Atribut status omogućava upravljanje zahtevima za prijem u privatne zajednice.

M:N Relacija 2 — Objave ↔ Tagovi
posts ⟷ tags
Vezna tabela: post_tags
— (bez dodatnih atributa)

Jedna objava može imati više tagova, jedan tag može biti dodeljen više objava. Ovo je čista M:N relacija bez dodatnih atributa — vezna tabela ima samo dva strana ključa. Tagovi su globalni i kreiraju ih administratori.

M:N Relacija 3 — Korisnici ↔ Objave (lajkovi)
users ⟷ posts
Vezna tabela: post_likes
liked_at DATETIME

Korisnik može lajkovati više objava, jedna objava može imati više lajkova od različitih korisnika. Kombinacija (user_id, post_id) je jedinstven ključ — duplikat lajkova nije dozvoljen. Atribut liked_at beleži vreme reakcije.

M:N Relacija 4 — Korisnici ↔ Korisnici (praćenje)
users ⟷ users
Vezna tabela: user_follows
follower_id INT (FK) following_id INT (FK) followed_at DATETIME

Self-referencing M:N relacija na tabeli users. Jedan korisnik može pratiti više korisnika (follower_id), a jedan korisnik može imati više pratilaca (following_id). Napomena: korisnik ne može pratiti samog sebe — ograničenje se implementuje na serverskom sloju.

Poglavlje IV

Replikacija i Failover

Aplikacija mora biti delimično otporna na otkaze, to se postiže uvođenjem distribuirane komponente sistema — upravljanje konekcijama ka MySQL bazi podataka u scenariju sa jednim Master čvorom i dva Slave čvora. Celokupna logika replikacije i failovera implementira se na nivou serverske aplikacije, u posebnom modulu koji se naziva db.ts (ili dbManager.ts).

Ključni princip: sve operacije pisanja (INSERT, UPDATE, DELETE) uvek idu isključivo na Master. Operacije čitanja (SELECT) distribuiraju se između dostupnih Slave čvorova radi ravnomerne raspodele opterećenja. Ako su oba Slave čvora nedostupna, čitanje pada na Master kao poslednju liniju odbrane.
IV.1 — Master-Slave replikacija

MySQL Master-Slave replikacija je mehanizam gde Master čvor beleži sve promene u binary log fajl, a Slave čvorovi kontinuirano čitaju taj log i primenjuju iste promene na sebi. Iz ugla aplikacije, replikacija je transparentna — aplikacija ne kreira replikaciju, već samo koristi već postavljene čvorove tako što svakom dodeljuje odgovarajuće upite.

U db.ts modulu definišu se tri odvojena mysql2 connection pool-a — po jedan za svaki čvor. Svaki pool ima definisan host, port, user, password i database koji se čitaju iz environment varijabli.

IV.2 — Health Check sistem

Health Check je mehanizam kojim aplikacija periodično proverava da li je svaki čvor baze dostupan i ispravno radi. Implementirati kao setInterval koji se izvršava svakih 10 sekundi i šalje SELECT 1 upit svakom čvoru.

Svaki čvor ima interno stanje koje se ažurira na osnovu rezultata health check-a. Stanja čvora:

✅
Healthy
Čvor odgovara na SELECT 1 unutar timeout-a. Uključen u pool za distribuciju zahteva.
⚠️
Degraded
Čvor odgovara, ali sa kašnjenjem iznad praga (npr. >500ms). Koristi se samo ako nema healthy čvorova.
❌
Unreachable
Čvor ne odgovara ili baca grešku. Isključen iz pool-a — zahtevi se ne rutiraju na njega.

Rezultati health check-a čuvaju se u memoriji servera (TypeScript objekat/Map). Stanje se izlaže kroz poseban GET /api/health endpoint koji Admin panel koristi da bi prikazao tabelu zdravlja čvorova u realnom vremenu.

IV.3 — Automatski Failover

Failover je procedura automatskog prelaska na rezervni čvor kada primarni prestane da radi. U ovom sistemu postoje dva tipa failovera:

Slave Failover (čitanje)

Kada Slave čvor postane Unreachable, health check ga označava kao nedostupnog. Sledeći getReadConnection() poziv ga automatski preskače. Ako nijedan Slave nije dostupan, čitanje se rutira na Master.

Master Failover (pisanje)

Kada Master postane nedostupan, sistem to detektuje kroz health check. Automatski se unapređuje (promote) Slave 1 u novu Master ulogu. Svi write zahtevi se preusmeravaju. Ova procedura se loguje u audit tabelu.

Master failover je najkritičnija procedura — tokom njenog trajanja kratko postoji prozor u kom pisanje nije moguće. Aplikacija mora ovaj slučaj da obradi elegantno: API vraća HTTP 503 Service Unavailable sa porukom dok failover nije završen. Ne sme doći do gubitka podataka.
IV.4 — Struktura db.ts modula

Cela logika replikacije enkapsulirana je u jednom modulu koji ostatak aplikacije uvozi. Modul izvozi:

  • getReadConnection() — vraća pool zdravog Slave čvora, ili Master ako nema Slave-ova
  • getWriteConnection() — uvek vraća Master pool
  • getHealthStatus() — vraća TypeScript objekat sa stanjem svakog čvora (za health endpoint)
  • startHealthCheck(interval: number) — pokretanje periodičnog health check-a
  • promoteSlaveToMaster(slaveIndex: number) — ručno ili automatsko promovisanje Slave-a u Master

Poglavlje VII

[OPCIONO] Deploy na Vercel i konfiguracija okruženja

Frontend React aplikacija deployuje se na Vercel platformu kao statički sajt. Vercel automatski detektuje Vite/CRA projekat, builduje ga i distribuira putem globalnog CDN-a. Backend (Node.js Express server) mora biti deployovan odvojeno na platformi koja podržava long-running servere — preporučeno Railway ili Render, a MySQL baza na PlanetScale, Clever Cloud ili Aiven (besplatan) servisu.

VII.1 — Koraci deploymenta
  1. Kreirati vercel.json u root-u frontend projekta sa konfiguracijom ruta (SPA redirect: sve rute → index.html)
  2. Pushati kod na GitHub repozitorijum i spojiti ga sa Vercel nalogom putem Vercel Dashboard-a
  3. U Vercel Dashboard-u postaviti Environment Variables — minimalno VITE_API_URL koji pokazuje na URL deployovanog backend-a
  4. Deployovati backend na Railway/Render — postaviti sve environment varijable za konekcije ka bazi
  5. Pokrenuti MySQL Master i Slave instance (lokalno za razvoj, cloud servis za produkciju)
  6. Verifikovati da je replikacija aktivna (SHOW SLAVE STATUS na Slave čvoru mora prikazivati Slave_IO_Running: Yes)
  7. Testirati health check endpoint (GET /api/health/db) — mora prikazati sve čvorove kao Healthy
  8. Simulirati pad Slave čvora i verifikovati da Round-Robin automatski preskače nedostupni čvor
VII.2 — Environment varijable

Sve osetljive vrednosti se nikad ne commituju u kod — čuvaju se isključivo u .env fajlu (lokalno) i u platformskim environment varijablama (produkcija). Frontend koristi samo varijable koje počinju sa VITE_.

VITE_API_URL
Puna URL adresa backend servera (npr. https://pulsenet-api.railway.app) — Frontend
JWT_SECRET
Tajni ključ za potpisivanje JWT tokena — min 32 karaktera, nasumičan string — Backend
DB_MASTER_HOST
Host adresa MySQL Master čvora — Backend
DB_MASTER_PORT
Port MySQL Master čvora (default: 3306) — Backend
DB_SLAVE1_HOST
Host adresa prvog MySQL Slave čvora — Backend
DB_SLAVE2_HOST

Pravila validacije

Celokupna validacija mora biti implementirana troslojno: klijentska (React + TypeScript) za trenutnu povratnu informaciju korisniku; serverska (validatori podataka) kao jedini pouzdan bezbednosni sloj koji se ne može zaobići; ograničenja baze podataka unutar CREATE TABLE SQL upita.
